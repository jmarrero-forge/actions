## Egress write policy (opt-in)

The threat: a later step of the job (a dependency's install script, a
third-party action, a test) sends the job's secrets or sources to a
host of its choosing. The runner's user holds the job's token and its
checkout, and without this it reaches the whole network but the
metadata service.

`egress: write-policy` turns it on. The action then sets
`egress.write-policy`, `egress.proxy` and `egress.rust-proxy` in the
host configuration ([`config.mjs`](../config.mjs)); the image refuses
it without `sandbox.lock-runner`, since a runner's user with sudo could
remove the rules. Off by default.

Every process of the runner's user and its subordinate uids after the
action, external actions and Runner.Worker itself included, is then held
to the proxy's policy: reads (GET, HEAD and OPTIONS without a body) go
anywhere not on the threat feed, and writes only where a `[[write]]`
rule allows.

Runner.Worker reads proxy settings only when it starts, before any step,
so nothing is asked to use the proxy. Instead nftables redirects each
new TCP connection of those uids to a public address on port 80 or 443
to the proxy's second listener, `127.0.0.1:3129`. The proxy decides TLS
by the server name the client asks for, and plain HTTP by its one
`Host` header, and connects where that name resolves, never to the
address dialed: TLS without a name is refused. Everything else of those
uids is refused: other ports, UDP (QUIC included), IPv6, private and
tailnet addresses, the metadata service. Loopback, DNS to the resolvers
of `/etc/resolv.conf` and connections opened before setup stay. The
sandbox user cannot reach the second listener.

### Trusting the proxy

Setup, as root, puts the proxy's per-job authority in the system's trust
store (`update-ca-certificates`, or `update-ca-trust` on RHEL), which
curl, git, OpenSSL, Go and .NET read, and writes
`/etc/egress-proxy/runner.env` for what does not read it. A step cannot
change a later step's environment except through `GITHUB_ENV`, so the
action appends that file's trust-store variables to it
([`runner-env.mjs`](../runner-env.mjs)): `NODE_EXTRA_CA_CERTS` for Node,
and so every JavaScript action, `REQUESTS_CA_BUNDLE` for Python's
requests and pip, and `SSL_CERT_FILE`. It refuses any other line of the
file. A tool that trusts neither fails closed; do not work around it by
turning certificate checks off.

The proxy ends TLS for every request of the runner's user, so it sees
what those requests carry: the job's token, the runtime and identity
tokens and any secret a step sends. A flaw in it reachable from a
fetched origin is worth those credentials.

### The runner's own writes

The runner's own writes (job and step status, logs, artifacts, caches,
summaries) pass by two built-in rules that only the redirected
connections get
(`policy.rs`): any write to `actions.githubusercontent.com` and the
names under it, and PUT to storage under `blob.core.windows.net`, where
the results service hands out signed upload URLs. GitHub documents only
`*.blob.core.windows.net` for storage, and actions/toolkit and
actions/runner name no account: they PUT to whatever URL the service
returns.

What remains open: the service rule is a write channel to anyone holding
a token for it, such as another repository's runtime token. In the
pinned image (v0.6.3) the storage rule admits **every** Azure storage
account, so a step can PUT the job's data to an account of its own with
a signed URL it made itself. agentic-job's main narrows it to the
twenty `productionresultssaN` accounts of gh-aw's `github-actions`
ecosystem, which still leaves any of them that is free to register; that
reaches this action only with a later pin.

## The policy file

A `GET`, `HEAD` or `OPTIONS` without a body may go to any host that is
not on a threat feed. Anything else, a WebSocket and a read with a body
included, needs a `[[write]]` rule. The image's rules allow `git fetch`
from six forges, `gh`'s GraphQL reads and `npm audit`. The proxy does
not read a GraphQL query, so a mutation passes it too: only GitHub's
enforcement of the token's permissions stops a write there. A push is
refused. So is a request whose `Host` header or TLS name is not the host
it connected to, and anything in a tunnel that is not HTTP.

The `egress-policy` input names a file of rules that replaces the
image's, never adds to them: CI's `egress-policy` job proves that with a
[fixture](../ci-egress-policy.toml) that leaves out the `npm audit` rule
and requires that POST refused. Choose policy files from the caller's
own trusted configuration, never from dispatcher-controlled inputs or
files a step produced. With `check`, keep the image's git fetch rule:
the check fetches from GitHub. The proxy parses the rules at setup, and
an invalid file fails setup (CI's `invalid-egress-policy` job).

A refusal is a 403 with the reason in `X-Egress-Denied`. The proxy's
log is one JSON line per request with method, host, path and decision,
never headers, bodies or query strings.

### Opt-in domain allowlist

An attacker can leak data in a GET URL to their own server even without
a request body. Write rules alone do not stop that. To restrict
destinations, add this table to the policy file:

```toml
[egress]
mode = "allowlist"
allow = ["example.com", "packages.example.org"]
```

This is the policy file's table, not the host configuration's
`[egress]`. Keep the `[[write]]` rules the job needs in the same file.

The gate applies to CONNECT and every HTTP request, including
destinations of redirects and writes. A write still needs its write
rule; the threat feed and Host/TLS-name checks still apply. Entries
match the named domain and all its subdomains on label boundaries,
ignoring case and one trailing dot. Use ASCII DNS names (punycode for
international names), not URLs, ports, wildcards or IP literals.
IP-literal destinations are refused in this mode. At most 256 entries of
at most 253 characters are accepted; an empty list denies every
destination.

An entry without a dot names one of
[gh-aw](https://github.github.com/gh-aw/)'s ecosystem identifiers, such
as `github`, `containers`, `node` or `python`, and stands for its group
of hosts, which count against the 256. An unknown identifier is refused.
Groups include shared hosting domains, such as `githubusercontent.com`
in `github`: allowing one delegates the risk to its other tenants.

Omitting the table, or `mode = "reads-anywhere"`, keeps reads open.

## Network

The nftables rules that always apply, whatever `egress` says:

- The cloud metadata service is refused to the sandbox user's uids at
  `169.254.169.254` always. With `sandbox.deny-runner-metadata` (on in
  [`hosted.toml`](../hosted.toml)) it is refused to the runner's user and
  its subordinate uids too, and EC2's IPv6 address `fd00:ec2::254` with
  it; in the pinned image (v0.6.3) the sandbox user's IPv6 refusal also
  comes only with that key. The threat is a step
  asking the metadata service for the instance's identity or, on a
  self-hosted cloud runner, the instance role's credentials, which the
  job never granted. Without the write policy that is the only rule on
  the runner's uids, and a `config` of the caller's that leaves the key
  out leaves the service open to every step.
- The rules reject rather than drop, and match subordinate uids, so
  rootless containers are covered.

[The sandbox user](../README.md#the-sandbox-user-opt-in) has rules of
its own. With `egress.proxy` on, which `egress: write-policy` sets,
everything of its uids is rejected but loopback, and loopback's port 53
with it: it reaches the network only through the proxy on
`127.0.0.1:3128`, by `HTTPS_PROXY` and the trust variables in its
environment. Without the proxy, [`hosted.toml`](../hosted.toml)'s default,
its network is open but for the metadata service. The proxy's own uid
is rejected on the tailnet and on private, loopback and link-local
addresses, except DNS to the literal resolvers of `/etc/resolv.conf`.
The loaded rules stay in `/etc/agentic-job/rules.nft`.

systemd-resolved, on the hosted Ubuntu image, resolves names for any
local user over its Varlink socket and the system bus, and asks upstream
as itself, so a user the rules refuse can still send data out in names.
`sandbox.close-resolved = true` (on in `hosted.toml`) takes every user
but root off the sockets in `/run/systemd/resolve/`, the runner's user
too, and installs a bus policy that refuses calls to
`org.freedesktop.resolve1` but root's and the runner's. Both refuse by
who connects, so a container's subordinate uids are refused too. It
needs systemd 258 or newer where resolved is socket-activated.

## What egress does not stop

- Reads are open, so data can leave in a `GET` to a host that is not on
  the feed, unless the allowlist above is on. The feed is fetched once,
  at setup and checked against a pinned commit and hash: a fetch that
  fails leaves the proxy without one, with a warning, and a file other
  than the pinned one fails setup.
- DNS to the resolvers stays a channel, for every user.
- The runner's built-in write endpoints above.
- Connections opened before setup.
- Agent jobs cannot opt in yet: a provider's API and the tailnet are
  refused through it.

For DNS/IP-only filtering, see
[step-security/harden-runner](https://github.com/step-security/harden-runner).
