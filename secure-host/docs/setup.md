for this action. The code is agentic-job's
[`sandbox/setup`](https://github.com/cgwalters-forge/agentic-job/tree/main/crates/agentic-job/src/sandbox).

## The image

The action runs the pinned image as root podman, with the host's root at
`/host` and the configuration as a path on the host:

```sh
sudo podman run --rm --privileged --pid=host --network=none -v /:/host \
  ghcr.io/cgwalters-forge/secure-host@sha256:DIGEST /path/to/config.toml
```

The image is `FROM scratch` with agentic-job's static binary and the
compiled world-write object. It has no shell or libraries, so it uses
the host's: it changes its root to `/host`, refuses an unsupported host,
installs the binary as `/usr/local/bin/agentic-job` (for `sandbox check`
and the probes) and the object under `/usr/local/lib/agentic-job/`, then
runs `secure-host apt`, `secure-host world-write` and `sandbox setup`
through the host's `nsenter -t 1`, in init's namespaces. The world-write
links are pinned in the host's bpffs and the egress proxy is a systemd
unit, so both outlive the container.

With the [write policy](egress.md) on, the proxy runs from the same
image: setup starts `egress-proxy.service` as `systemd-run … podman run
--pull=never ID` in root podman. The proxy is then the attested binary
from root's image store, and its unit and container are root's, which
the runner's user cannot stop after the lock. Inside, it runs as the
`egress-proxy` user on the host's network, with no capabilities, a
read-only root and only its policy, state and log directories mounted,
each with `:Z` for SELinux on RHEL 10 (untested there).

`sudo` does not pass `SUDO_USER` into the container: the action names
the runner's user with `sandbox.runner-user`
([`config.mjs`](../config.mjs)).

## Supported hosts

Exactly Ubuntu 26.04 and RHEL 10 (with its minor releases), by `ID` and
`VERSION_ID` of `/etc/os-release`, not `ID_LIKE`: Fedora, CentOS Stream
and other derivatives are refused. The image refuses any other host, or
a missing release file, with one diagnostic before it changes apt,
loads the policy or sets anything up. Admission proves no kernel feature;
the setup checks and probes still have to pass.

The machine must be thrown away after the job. `sandbox setup` refuses
one it has set up before (`/etc/agentic-job` exists), and a failed setup
can leave partial changes that make the host unfit for reuse.

## What the step does to the host

In order, once:

1. **apt.** `secure-host apt` replaces `azure.archive.ubuntu.com` with
   `archive.ubuntu.com` in the runner's apt sources, leaving fallbacks,
   security mirrors, suites and signing intact, and sets 10-second HTTP
   timeouts with three retries. A stalled package body otherwise holds
   the step for minutes.
2. **The [world-write policy](world-write.md)**, and the
   [runner-read rule](runner-reads.md) when the configuration asks for
   it.
3. **`sandbox setup`** as root:
   - a preflight that refuses a host that is not fresh, has no
     world-write policy loaded, or would read a sudoers.d file after
     setup's own;
   - creates [the sandbox user](../README.md#the-sandbox-user-opt-in),
     `runner-sandbox`, with its own home and subordinate uids, and
     closes to it the runner's home (mode 0700), `/opt/hca`,
     `/var/run/tailscale` and `sandbox.private-dirs`; drops
     `XDG_RUNTIME_DIR` and any `ACTIONS_*` variable from
     `/etc/environment`; denies it sudo, every polkit action, cron, at
     and lingering;
   - remounts `/proc` with `hidepid=invisible`: other users' processes
     cannot be listed or read, command lines included. Secrets must
     still never be passed as command-line arguments;
   - stops the units of `sandbox.stop-services`, with the sockets,
     paths and timers that trigger them, and masks them until reboot;
     the container daemon first of all;
   - with `sandbox.close-resolved`, closes systemd-resolved
     ([egress](egress.md#network));
   - installs `setup.packages` as root, only those not already
     installed, with `--no-install-recommends`;
   - checks the privileged-binary allowlist (below);
   - starts the egress proxy when configured, and loads the network
     rules;
   - raises `ptrace_scope` from 0 to 1;
   - installs the root-owned helper and configuration under
     `/etc/agentic-job/`;
   - last, the lock (below).
4. **`sandbox check`**, as the runner's user, unless `check: false`
   ([probes](probes.md)).

Setup logs `Sandbox setup stage NAME: SECONDSs (ok|failed)` for every
stage and `Sandbox setup total: …` after them. These cover setup only,
not pulling the image, loading the policy or the probes.

### The lock

`sandbox.lock-runner` (on in [`hosted.toml`](../hosted.toml)) takes root
from the runner's user:

- **sudo**: a rule read last denies it everything, and one after it
  grants `/usr/local/libexec/agentic-job helper *` as root without a
  password. `sudo -l` still lists the image's own grant before them;
  what counts is the last.
- **polkit**: the first rule read answers `NO` for the runner's user,
  which covers `pkexec`, `run0` and `systemctl start`.
- **su**: root's account is locked if it had no password. One it has is
  only noted, and `su` stays a way to root for whoever knows it: use an
  image whose root has none.
- **sudo from a directory service**: an nsswitch that takes sudo rules
  from one as well is noted, not refused; such a rule could grant sudo
  again after the lock.
- **groups**: a process keeps the groups it started with, so `docker`
  is still in a step's `id -G` after the lock. The lock does not rely on
  membership: for each group that is root by another name it closes
  what the group leads to. The daemons of `docker`, `podman`, `lxd`,
  `incus` and `libvirt` are stopped, sockets included; block devices
  lose group and other access (`disk`); the password files are closed
  (`shadow`). `adm` and `systemd-journal` read the host's logs, which is
  not root; they are noted.

The helper is the one privileged command left. Its interface is closed:
fixed operations (sandbox entry, process cleanup, proxy-log reads and
probe controls), none taking a path, a user or a command that root then
acts on. It runs every program from a fixed PATH whose directories must
be root's alone, with none of the caller's environment, and reads the
sandbox user from the root-owned configuration.

`sandbox.lock-runner = false` keeps the runner's sudo and gives up
everything this action claims; CI's `options` job uses it to show the
`config` input is taken.

### The privileged-binary allowlist

After packages, setup stats the paths in agentic-job's
[`privileged-binaries.tsv`](https://github.com/cgwalters-forge/agentic-job/blob/main/crates/agentic-job/src/sandbox/setup/privileged-binaries.tsv),
following links. A listed path absent from the image is skipped; one
present with a different type, owner, group or mode refuses setup. It is
a metadata check of known binaries, not an inventory: it does not search
the filesystem, and neither finds nor strips unknown setuid programs.
File capabilities are not looked for. A trusted fresh image is assumed.

Root processes in the job's cgroup besides setup's own are listed, never
killed: on the hosted runner the job shares its cgroup with the
platform's `provjobd`.

## What a job has to know

**Order: everything that needs root comes before the step.** Package
installs, a `setup-*` action that writes outside the runner's own
directories, starting a service, joining a tailnet, pulling or building
with the container daemon. After it:

| What | After the step |
| --- | --- |
| `run:` steps, JavaScript actions | work, as the runner's user |
| `actions/checkout`, `actions/cache`, `actions/upload-artifact`, a Rust or Node cache | work: they read and write the runner's own files. A cache's post step saves after the lock |
| `setup-node`, `setup-python`, `setup-go` and the like | work where they install into the runner's tool cache; one that calls `sudo` does not |
| `sudo` anything, `apt-get`, writing under `/etc` or `/usr` | refused |
| `docker`, Docker container actions, `services:` and `container:` on the job | gone: the daemon is stopped, since its group is root by another name. Rootless podman, installed before the step, is the container tool later steps have |
| A post step that calls `sudo` | fails or warns, as that action decides: a network join's logout has to only warn, and leave a node that expires by itself |

CI exercises `run:` steps, an artifact upload, and `sudo` and `docker`
refused. The rest follows from who owns which files.

Diagnostics of setup and the probes have both workflow-command syntaxes
broken up (`::` becomes `: :`, `##[` becomes `## [`), so that no line
of theirs can become a command to the runner.

### Containers

The action installs podman where it is missing, without recommended
packages, so not necessarily its uid-mapping helpers or rootless
networking (`passt`, `slirp4netns`). On Ubuntu, install them before the
action:

```yaml
- run: sudo apt-get update && sudo apt-get install -y podman uidmap passt
- uses: cgwalters-forge/actions/secure-host@COMMIT
```

With the write policy on, nothing has to be told about a proxy: a
rootless container's connections are made by the runner's uids, so the
nftables redirect takes them to the proxy as it does a step's. What the
container needs is to trust the proxy's per-job authority. Mount the
public CA bundle read-only where the image expects its trust bundle; the
host network is the tested shape. For Alpine and Debian/Ubuntu images:

```sh
podman build --network=host \
  -v /etc/egress-proxy/ca-bundle.pem:/etc/ssl/certs/ca-certificates.crt:ro \
  -t local-build .
podman run --rm --network=host \
  -v /etc/egress-proxy/ca-bundle.pem:/etc/ssl/certs/ca-certificates.crt:ro \
  local-build
```

For Fedora/RHEL images, mount at `/etc/pki/tls/certs/ca-bundle.crt`.
The image must have that destination. Tools with trust stores of their
own need the bundle configured there too. The mounts apply to the
build's `RUN` steps or the running container, not the resulting image.
A container on a network of its own, rather than the host's, is not
tested here.
The mount holds public certificates, not the proxy's key; host
networking grants no root and bypasses no rule of the container's uids.

The host's `hidepid` applies to rootless podman's host processes too; a
container's own `/proc` shows its PID namespace.

## Without the action

The action is the image; a job on another CI system can run the same
commands itself, from agentic-job's binary, after loading the
world-write policy with `agentic-job secure-host world-write` (setup
refuses a host without it):

```sh
sudo install -m 0755 agentic-job /usr/local/bin/agentic-job
sudo /usr/local/bin/agentic-job sandbox setup --config host.toml
agentic-job sandbox check
```

`agentic-job config --host` writes such a file from single settings
(`--boolean sandbox.lock-runner=true`), each taken as the value of one
key and never read as TOML; the action builds its configuration that
way. Installed or linked as `secure-host`, the binary offers only the
host's commands and refuses any table but `[sandbox]`, `[egress]` and
`[setup]`.
