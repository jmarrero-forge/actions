## What it assumes

Any step after the action may be hostile: a build script from a pull
request, a dependency's install hook, a third-party action, an agent
whose prompt was injected. What then matters is what that step can
reach. The action does not make such a step trustworthy; it takes away
root and other users' world-writable files, and with the default
[`hosted.toml`](../hosted.toml) the metadata service and other
processes' environments, so that a job built as the contract says holds
nothing else worth stealing but the tokens every step already has and
the Worker's memory ([not claimed](#not-claimed)). Those two are keys of that file
(`deny-runner-metadata`, `deny-runner-reads`), off in the image: a
caller's `config` replaces the file whole and must set them itself.

The machine is a VM used for one job and thrown away. The boundary is
the kernel's uid and BPF checks on one kernel, not a container or a
virtual machine: a kernel flaw crosses it, and so does local IPC that
answers any user (the system bus, a world-connectable socket), which the
check finds and the configuration has to stop or allow by name.

## Actors and trust

The caller's maintainers choose the runner, the pinned action, its
configuration and the policy files. They are trusted, and so is the ref
those come from: read configuration from the repository's default
branch or its variables, never from a workflow input a dispatcher sets.
The CI platform, kernel, systemd, sudo, nftables, podman, the image's
signer and the runner image are trusted too.

Every step after the action, and every text those steps read, is not.

## What a later step can count on, and what it cannot

**No step after this one has general root access.** Not a `run:` step,
not another action, not a post step, not the runner's own cleanup. So
nothing later in the job can undo the action: load a kernel module,
change the network rules, stop the proxy, read what only root reads, or
leave something behind as root. The one privileged command left to the
runner's user is the helper's fixed operations
([setup](setup.md#the-lock)).

**The runner's user is still the runner's user.** The lock takes its
root, not what it owns. A step reads the checkout, the caches, the job's
token and every secret a step is given, and can change the files of the
actions the job has downloaded, whose post steps run later. Its network
is open but for the metadata service, unless the
[write policy](egress.md) is on.

**It secures what runs after it.** A step before it runs with the
runner's sudo, and nothing holds a job to the order but review and,
for a repository that runs it, agentic-job's `workflows check`, which
refuses a job whose steps before this one are not on a short allowlist.
A root service started before the action that does what a local user
asks defeats the lock: nothing in a job should start one.

## One trust level for the rest of the job

Every step after the action, `run:` or `uses:`, a third-party action and
its post step included, runs as the runner's user. That user is the
unprivileged thing; no second user is needed for a job to be safe from
its own later steps.

What a confined step can still do with the job's tokens (runner 2.337's
source, read for agentic-job#501):

- The runner gives every JavaScript and container action
  `ACTIONS_RUNTIME_TOKEN`, with the artifact, results and cache service
  URLs. A step can upload or replace this run's artifacts and write
  cache entries in the run's scope. A run started by `push`,
  `workflow_dispatch` or `schedule` on the default branch writes the
  scope that later branches and pull requests restore from; a
  `pull_request` run writes only its merge ref.
- A `run:` step gets `ACTIONS_ID_TOKEN_REQUEST_TOKEN` when the job has
  `id-token: write`, and can mint identity tokens for any audience.
- Any step can steer later ones: `GITHUB_ENV` refuses only
  `NODE_OPTIONS`, so `LD_PRELOAD` or `BASH_ENV` set by one step reach
  every later action. The workspace, the home and the downloaded actions
  under `_work/_actions` are the runner's user's files.

So a job that runs code it does not trust holds no `id-token`
permission and no secrets, and treats its own artifacts and cache
writes as that code's output, which a separate job validates as data.
Step-to-step tampering is out of scope: any step can compromise the
steps after it, and that cannot be fixed inside one job.

## Requirements

### R4. The runner's user loses root before untrusted steps run

Setup locks general sudo and polkit and closes root-equivalent group
access by default. It validates known privileged binaries' metadata and
refuses a host without the world-write policy. Setuid-root programs no
package owns are not searched for, so a trusted image without such
helpers is required. The runner keeps only the helper's fixed
operations. `ptrace_scope` is raised to at least 1. The runner's probes
test these ([probes](probes.md#after-setup-nothing-has-root)).
`sandbox.lock-runner = false` gives this up. Privileged services the
image already runs, and kernel flaws, are outside the lock's guarantee.

### R10. What the guarantees depend on

A disposable Ubuntu 26.04 or RHEL 10 VM with systemd 257 or later, sudo
and nftables; the hosted `ubuntu-26.04` image is the one tested. A
trusted, protected ref for the configuration and policy files. Minimal
job permissions, `persist-credentials: false`, no `id-token` and no
secrets in the job that runs untrusted code.

### R11. Lints are not boundaries

`workflows check` and actionlint catch a job that breaks the contract;
they enforce nothing at run time. A job that skips them, or runs a step
before the action, gets no protection from them.

## Not claimed

- Separation of one step from another, or from the job's tokens.
- Protection from steps before the action, or from trusted maintainers.
- Confidentiality of data through reads and DNS: data can leave in a
  name lookup, and in a `GET` URL to any host the policy lets a step
  read, which is every host unless its [allowlist](egress.md#opt-in-domain-allowlist)
  is on.
- The Worker's memory, without `sandbox.unlink-worker-diagnostics`,
  which the default configuration leaves off: any step can have the
  Worker dump it through its .NET diagnostic sockets
  ([runner reads](runner-reads.md#the-workers-diagnostic-sockets)).
- Availability: a step can consume the machine until the job's timeout.
- A kernel or VM boundary.
