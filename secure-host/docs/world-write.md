## Access-time world-write policy

The threat: an unprivileged process changes another user's
world-writable file, or creates and removes entries in another user's
world-writable non-sticky directory, on the root filesystem. A runner
image leaves such paths behind, and a root process or a later trusted
step may read them.

The image always loads the policy, before setup and while it still has
root; there is no input to turn it off. No user but the owner may change
a world-writable file or non-sticky directory on the root filesystem,
decided when the change is attempted. Root is not exempt: a root process
may change what root owns, but not a world-writable object of another
user's on the root filesystem. Sticky directories such as `/tmp` are
allowed; a sticky regular file is not exempt. `sandbox setup` refuses a
host where the policy's links are not pinned, before it changes
anything.

The predicate compares the inode's owner with the task's kernel `fsuid`.
It has no group, user-namespace or root exemption. The loader records
the root filesystem's kernel device number before enabling it; other
superblocks are outside the policy, bind mounts of the root filesystem
inside it. The hooks are modify-return programs on `security_*`
wrappers, the same on both supported hosts whatever the active LSM list:

- `security_inode_permission`, for `MAY_WRITE`: file write access and
  parent-directory write permission for create, link, unlink, rename
  (both parents), mkdir, rmdir, symlink and mknod;
- `security_file_open`, for `FMODE_WRITE`: opening a file for writing;
- `security_file_permission`, for `MAY_WRITE`: writes through
  descriptors opened before activation, or before ownership or mode
  changes;
- `security_inode_setattr`, for `ATTR_SIZE`: truncate and ftruncate.

The fifth program is the [runner-read rule](runner-reads.md).

### Loading

The loader needs `runuser` (util-linux) and bpftool, which it installs
where `bpftool version` fails: on Ubuntu `linux-tools-common` and
`linux-tools-$(uname -r)`, on RHEL 10 the `bpftool` package. The hosted
`ubuntu-26.04` image already has them. The host needs no compiler: the
image carries the compiled object.

Loading is `bpftool prog loadall OBJECT PIN/links autoattach pinmaps
PIN/maps`. Each program's pin under `/sys/fs/bpf/agentic-job-world-write/links`
must be a tracing link, not a program pin: bpftool can fall back to
pinning an unattached program, so the loader checks every link. Then one
map update sets the root device and enables the policy. Pins are root's
alone and outlive the loader.

Before enabling, the loader proves a root-owned mode-0666 file on `/` is
writable as `nobody`; after, that the same write fails with `EACCES`,
while a mode-0666 file owned by `nobody` stays writable. Any load,
attachment, map-update or probe failure fails the step; there is no
fallback. On failure, partial attachments are left in place: the job
must not continue with untrusted code, and reuse of that host is
unsupported.

### What a refusal looks like

A refused write is an ordinary `EACCES` ("Permission denied") that names
neither the policy nor the owner, and the policy logs nothing. A write
that fails although the mode bits allow it, to a world-writable path on
the root filesystem that the writer does not own, is most likely this
policy.

### Overlays and containers

Rootful Podman's storage is on the root filesystem. In an overlay whose
upper and work directories are there, overlayfs repeats the access on
the upper inodes with credentials of its own:

- Write, unlink and both renames are allowed: overlayfs checks the upper
  inode again and unlinks and renames with the mounter's credentials.
- Create is refused: overlayfs creates the upper entry with the caller's
  fsuid, so the policy sees the caller creating in a root-owned,
  world-writable, non-sticky directory.

So in a container whose storage is on the root filesystem, a non-sticky
world-writable directory is closed to creation by anyone but its owner,
and any world-writable upper-layer object owned by someone other than
the mounter is refused even through the overlay: in a rootful container,
an object not owned by root; in a rootless container of the runner's
user, rootless podman's default storage under its home, an object of a
container user other than the one mapped to the runner's user. A build
that hits a plain `EACCES` there is most likely this. agentic-job's
hosted test runs these cases on overlays, with no Podman.

### What it does not cover

- Other filesystems: tmpfs, a second disk.
- Writable mappings made before activation. A new shared writable
  mapping needs a descriptor opened for writing, which the policy
  refuses; but a mapping made before activation keeps writing to the
  page cache, and `security_file_permission` stops `write(2)` on an
  early descriptor, not stores through memory. In this action the policy
  is active before any untrusted step runs, so no untrusted process
  holds one.
- Setuid programs (below).

It must not be described as complete write protection.

## What went with the walk

The policy replaced a walk agentic-job's setup used to make over the
whole root filesystem, taking world write off every path it found and
the setuid bit off setuid-root programs no package owned. On the hosted
image the walk took about two minutes. A configuration that still names
its switch, `sandbox.world-write-walk`, is refused.

The setuid inventory is not replaced. Setup checks known privileged
binary paths against an allowlist of their owner, group and mode
([setup](setup.md#what-the-step-does-to-the-host)) and searches for
nothing else, so the runner image must be a trusted fresh one without
arbitrary setuid-root helpers.
