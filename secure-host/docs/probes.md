# What `sandbox check` proves

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

Taken from agentic-job's `docs/sandbox-check.md`, for this action. With
`check: true`, the default, the action's last step runs `agentic-job
sandbox check` as the runner's user, and the step fails if a probe does.

Each probe is something a user tries and must not manage. Each has a
positive control, the same attempt somewhere it should work, so that a
probe which fails because a program is missing does not read as a
protection that holds. A probe or a control that comes out wrong fails
the check. Every line of output starts with `ok` or `FAIL` and the
probe's name in brackets; the names are stable.

Refusals the sandbox user makes run at most eight at a time, and each
first prints a line from inside the user's session: one without it is an
error, since a session that never started would otherwise read as a
refusal that holds. A refusal from a container that exits 125, 126 or
127, podman's own statuses for a container or command it did not start,
is an error for the same reason.

## After setup, nothing has root

The runner's user's probes, of [the lock](setup.md#the-lock):

| Probe | The runner's user tries to | Control | What stops it |
| --- | --- | --- | --- |
| `runner-sudo`, `runner-sudo-list` | run `sudo -n true`; ask `sudo -l /usr/bin/true` whether it may | `sudo-control`: root runs the helper's `ping` for it | the deny rule |
| `runner-sudo-rules` | (none: the rules `sudo -n -l` lists must end with the deny rule and the helper's) | the same | the two rules, read last |
| `runner-pkexec`, `runner-run0` | run a command through `pkexec` from a shell; run `run0 true` | `polkit-control`: root runs pkexec through the helper | the polkit rule |
| `runner-su` | become root with `su` | `su` runs at all | root's locked password, and no terminal to ask at |
| `runner-group:GROUP` | for each group it is in that is root by another name: connect to the daemon's sockets (`docker`, `podman`, `lxd`, `incus`, `libvirt`), write a block device (`disk`), read `/etc/shadow` (`shadow`) | it connects to a socket opened for it | the daemon is stopped; the devices and files are closed |
| `runner-world-write` | create a file in `/etc/agentic-job/world-write-probe` or append to its `file` | it creates a file in its own home | the world-write policy |
| `runner-metadata`, `runner-metadata-v6` | reach the metadata service, with `sandbox.deny-runner-metadata` | none after setup: CI's control is before the action | the rules on its uids |
| `worker-diagnostics` | (none: lists `Runner.Worker`'s diagnostic sockets still linked, with `sandbox.unlink-worker-diagnostics`) | | the unlink |

### What the final probe proves

Setup plants `/etc/agentic-job/world-write-probe`, a root-owned
mode-0777 directory that is not sticky, and in it `file`, root-owned
mode 0666. Ordinary permissions let any user create in the one and
append to the other. `runner-world-write` tries both as the runner's
user and `world-write` as the sandbox user; each must fail. Their
controls, `runner-world-write-control` and `world-write-control`, make
the same attempt in each user's own home. The probe reads no denial log:
it proves the policy by what it does.

## The sandbox user's probes

[The sandbox user](../README.md#the-sandbox-user-opt-in) exists by
default, so the check probes it too. agentic-job's `run` adds `token-*`
probes of its own, which `sandbox check` does not make.

| Probe | The sandbox user tries to | Control | What stops it |
| --- | --- | --- | --- |
| `sudo` | run `sudo -n true` | root runs the helper's control | a sudoers rule, read last |
| `polkit` | run a command through `pkexec`, from a shell | root can | a polkit rule, read first |
| `groups` | (none: lists its groups) be in a group that is root by another name | it lists its groups | setup gives it none of them |
| `linger` | keep its user manager alive after its sessions | logind lists its sessions | the polkit rule |
| `environ-self`, `environ-runner` | read the environment of the checking process, and of a second process of the runner's that holds a canary | the runner reads the canary there | the separate uid |
| `proc-other-users` | list or read `/proc/PID/cmdline` of PID 1, the checker or a runner-owned decoy | the runner reads the decoy; each entry reads its own process | `/proc` with `hidepid=invisible` |
| `environ-canary`, `environ-job-variables` | find the canary, or `ACTIONS_` in any variable, in any environment it can read | it reads its own processes' environments | `run0` passes on none of the caller's environment |
| `env-job-variables`, `oidc-value:NAME` | see `ACTIONS_*` variables in its own environment, or the identity-token request variables' values in any process it can read | it runs `env`; the checker has the variables | the same, and refusal by name |
| `private-dir:DIR` | list or enter the runner's home, `/opt/hca`, tailscaled's socket directory, `sandbox.private-dirs`, and the job's work directories | the runner lists its home | mode 0700 |
| `world-write` | as for `runner-world-write` above | it creates a file in its own home | the world-write policy |
| `ptrace-scope` | (none: reads the kernel setting) | | setup raises it to 1 |
| `crypto-policies` | (none: lists what under `/etc/crypto-policies` is world-writable) | | setup takes group and other write off it |
| `cron`, `at` | install a crontab; use `at` | the runner's user may | `/etc/cron.deny`, `/etc/at.deny` |
| `service:UNIT` | (none: the unit is inactive and masked, or not on the host) | journald is active | `sandbox.stop-services` |
| `resolved-bus`, `resolved-varlink` | resolve a name through systemd-resolved, over the bus and its Varlink socket | the runner's user resolves it | `sandbox.close-resolved` |
| `local-sockets`, `local-tcp` | connect to every listening Unix socket and local TCP port | it reaches two listeners opened for it | stopping the daemon, or naming the socket as allowed |
| `tailscale-status`, `tailscale-localapi` | use tailscaled's LocalAPI | root can | its socket directory is closed |

The `filesystem-view*`, `container-build` and `container-built-run`
probes run only with `sandbox.filesystem-view`, an opt-in read-only view
for the sandbox user that agentic-job's `docs/sandbox.md` describes.

## The network probes

| Probe | The sandbox user tries to | Control | What stops it |
| --- | --- | --- | --- |
| `network-control`, `container-pull`, `container-control` | (controls: reach a public page on the host and from a rootless container, through the proxy when there is one) | | |
| `metadata`, `container-metadata` | reach the metadata service, on the host and from a container | the runner's user reaches it, unless refused it | the rules on its uids |
| `egress-read`, `egress-cargo`, `egress-npm`, `egress-git` | (controls through the proxy: read a page, fetch a crate, install an npm package, fetch from git) | | |
| `egress-post`, `egress-push`, `egress-fronting`, `egress-container-post` | POST to a host with no write rule, push to a forge, name another host in `Host` than it connected to | the proxy's own 403, with `X-Egress-Denied` | the proxy's policy |
| `egress-direct`, `egress-tcp`, `egress-container-direct`, `egress-container-own-network` | reach the public page around the proxy | the runner's user opens the same connection | everything but loopback is rejected for its uids |
| `egress-resolve`, `egress-dns` | resolve a name; reach a public DNS server | the runner's user does both | the same, and loopback's port 53 |
| `egress-wireserver`, `egress-wireserver-dns` | reach Azure's WireServer over HTTP and its DNS port | the runner's user, where it can | the same |
| `egress-proxy-metadata`, `egress-proxy-wireserver` | have the proxy reach the metadata service or the WireServer | | the rules on the proxy's own uid |

The `egress-*` rows need the proxy, which `egress: write-policy` starts
(or a caller's `config` with `egress.proxy = true`); without it the
metadata refusal is the one the rules make. A
control the runner's user cannot make either (no WireServer on this
cloud) is printed as a note and the probe stands without it. The cargo
and npm rows are skipped, with a note, when the sandbox user has no
such program.

With the [write policy](egress.md#egress-write-policy-opt-in) the
runner's user is held to the proxy too, so most of the runner's
controls above become notes, and three rows are added:

| Probe | Who tries to | Expected | What makes it so |
| --- | --- | --- | --- |
| `write-policy-read` | the runner's user, with no proxy set, reads `https://example.com/` | succeeds | the redirection to the transparent listener, and its authority in the trust store |
| `write-policy-post` | the runner's user, with no proxy set, POSTs there | the proxy's own 403, with `X-Egress-Denied` | the proxy's policy |
| `write-policy-listener` | the sandbox user connects to the transparent listener | refused; the runner's user is the control | the rule on the sandbox's uids |

## Local sockets

The uid boundary covers files and processes. A daemon that listens where
any user may connect is on the other side of it all the same: a
container daemon, a package manager's API, an SSH server. So the check
starts a copy of itself as the sandbox user, which reads
`/proc/net/unix` and `/proc/net/tcp`, tries each listener, and reports
what let it in. An abstract socket has no permissions and is reported
without a try.

What may be there without failing the check is a short list in
agentic-job's `sandbox/check/on_host.rs`: the system bus, the journal's
and the user database's sockets, PID 1's notification socket, the
Varlink services directly under `/run/systemd/`, systemd's notification
datagram sockets, polkit's password helper, and the user's own under
`/run/user/UID/`. Anything else fails the check until the configuration
stops the daemon with `sandbox.stop-services` or names the socket in
`sandbox.check.allow-sockets` or `allow-tcp-ports`, as
[`hosted.toml`](../hosted.toml) does for systemd-networkd. Another
runner image listens on other sockets and needs a configuration of its
own.

It does not see UDP, a listener bound only to an IPv6 link-local
address, nor services behind the system bus that ask polkit nothing.

## The job's work directories

The runner's home is closed, and on the runners we know the job's work
and temporary directories are inside it. Where they are not, the check
also tries the directory it runs in and those named by `RUNNER_TEMP`,
`RUNNER_WORKSPACE` and `GITHUB_WORKSPACE`, when they are the runner's
own and outside what setup closed. A configuration with such a layout
lists them in `sandbox.private-dirs`.
